# Research: Unified Production Graph

This document records the design decisions and architectural trade-offs for the Unified Production Graph (`src/agents/production-graph.ts`), its dynamic routing classifier, and node-attributed traces.

---

## Decision 1: LangGraph `StateGraph` as the Workflow Engine

**Decision**: Implement `createProductionGraph` using `@langchain/langgraph`'s `StateGraph` and `Annotation.Root`. The graph topology consists of 6 discrete nodes:
1. `context` (linear from START)
2. `router` (linear from `context`)
3. `react` (conditional branch from `router`)
4. `plan-and-execute` (conditional branch from `router`)
5. `reflect` (conditional branch from `router`)
6. `response` (converging target from all three strategies, linear to END)

**Rationale**:
- OpsPilot already uses LangGraph for `plan-and-execute` (`src/agents/plan-and-execute.ts`).
- Moving from procedural orchestration in `chat-service.ts` to an explicit state graph allows each step (context preparation, routing decision, strategy execution, response persistence) to be isolated, testable, and transparent.
- LangGraph conditional edges (`addConditionalEdges`) cleanly evaluate the routing decision or manual override to route to exactly one strategy node.
- All three strategy branches converge cleanly to the `response` node before reaching `END`.

**Alternatives considered**:
- *Procedural if/else in `chat-service.ts`*: Rejected because it maintains coupling, hides routing rationale from graph visualization, and does not provide an explicit execution graph with node transitions.
- *Multiple standalone sub-graphs without convergence*: Rejected because response persistence, metric aggregation, and background learning reflection must execute consistently regardless of the selected strategy.

**In-repository references**:
- `src/agents/plan-and-execute.ts` (lines 517-538): demonstrates `StateGraph`, `addNode`, `addEdge`, and `addConditionalEdges`.
- `Autonomous-Agent.md` (lines 2367-2420): defines the target OpsPilot graph topology.

## Decision 2: Router Node with `withStructuredOutput` and Prompt Decision Table

**Decision**: The `router` node uses `createModel().withStructuredOutput(RouteDecisionSchema)` when no manual strategy override is present. The system prompt contains an explicit markdown decision table categorizing operational requests into the three strategies:
- `react`: Single-tool queries, direct operational lookups, status checks, listing firing alerts.
- `plan-and-execute`: Multi-step investigations, sequenced maintenance, cross-service incident correlation.
- `reflect`: Critical operations, high-severity incident resolution (`critical`/`high`), ambiguous multi-factor alerts requiring verification before committing answers.

The structured output schema produces:
```ts
export const RouteDecisionSchema = z.object({
  route: z.enum(["react", "plan-and-execute", "reflect"]),
  reason: z.string().min(1).describe("Explanation of why this strategy was chosen based on the decision table."),
});
```

If the LLM call fails, the router falls back safely to `"react"` with an explanatory reason in the trace to prevent request failure.

**Rationale**:
- `withStructuredOutput` guarantees schema compliance and eliminates brittle regex or JSON parsing in domain code.
- Including a decision table directly in the system prompt grounds the model's classification criteria, ensuring reproducible and testable choices across prompt archetypes.
- Emitting a dedicated `"route"` event in the trace makes autonomous routing decisions fully auditable.

**Alternatives considered**:
- *Heuristic keyword matching (regex)*: Rejected because natural language requests in incident management have subtle nuances (e.g. "check status and if bad, resolve incident" vs "check status") that require semantic classification.
- *Unstructured classification with post-hoc parsing*: Rejected due to potential parsing errors and lack of strict boundary validation.

## Decision 3: Mandatory `node` Field Across All Trace Events

**Decision**: Extend `TraceEventSchema` so that every event variant includes a required `node: z.string().min(1)` property. All events emitted during graph execution are stamped with the originating node name:
- `"context"`: for summarize events generated during context window compression.
- `"router"`: for the new `"route"` trace event.
- `"react"`: for actions, observations, thoughts, and answers generated by the ReAct strategy.
- `"plan-and-execute"`: for plans, actions, observations, and answers generated by the Plan-and-Execute engine.
- `"reflect"`: for critiques and revision thoughts generated during reflection loops.
- `"response"`: for any terminal response-stage trace markers.

Define a new `RouteTraceEvent` variant in the `TraceEvent` discriminated union:
```ts
export const RouteTraceEventSchema = z.object({
  type: z.literal("route"),
  node: z.literal("router"),
  route: z.enum(["react", "plan-and-execute", "reflect"]),
  reason: z.string(),
  override: z.boolean().optional(),
}).strict();
```

**Rationale**:
- Provides complete "X-ray" observability of the graph execution without guessing which component produced which tool action or thought.
- Essential foundation for future trace persistence, auditing, and observability (U7).
- Ensures backward compatibility in trace readers while enriching data structure.

**Alternatives considered**:
- *Separate node traces array*: Rejected because preserving chronological order in a unified trace stream is critical for debugging incident workflows.
- *Optional `node` field*: Rejected because the specification explicitly mandates `node` in *every* trace event.

## Decision 4: Strategy Override Handling in `/chat` and Graph State

**Decision**:
1. In `src/http/server.ts`, update `ChatRequestSchema` to leave `strategy` as optional without defaulting to `"react"`.
2. When `strategy` is omitted (`undefined`): The request state passes `strategyOverride: undefined`. The `router` node executes LLM classification.
3. When `strategy` is provided (e.g. `"react"`, `"plan-and-execute"`, `"reflect"`): The request state passes `strategyOverride: strategy`. The `router` node skips the model invocation, logs a `"route"` event with `override: true`, and immediately selects the requested strategy.
4. Support `reflect: true` flag in `/chat` as an alias or modifier for the `"reflect"` route when `strategy` is omitted or set to base strategies.

**Rationale**:
- Preserves full backward compatibility with existing tests and clients that specify an explicit strategy.
- Guarantees zero latency and zero LLM cost for automated benchmarks or tests that explicitly request a specific strategy.
- Explicitly flags overrides in the trace (`override: true`), keeping audit logs accurate.

**Alternatives considered**:
- *Bypass graph completely on override*: Rejected because context assembly, trace formatting, conversation persistence, and response metrics must still follow the standardized graph lifecycle.
- *Require separate endpoint for unrouted chat*: Rejected because the user requirement explicitly modifies `/chat` to make `strategy` optional.
